## Overview

**Audit Logs** in Bifrost Enterprise record administrative activity so operators can review who changed what, when it happened, and which resource was affected.

Audit log entries can be signed with an HMAC key, retained for a configurable number of days, viewed in the dashboard, and exported for downstream review.

### Key Features

| Feature              | Description                                                                                   |
| -------------------- | --------------------------------------------------------------------------------------------- |
| **Signed events**    | Configure an HMAC key so audit entries can be verified.                                       |
| **Dashboard review** | View audit entries from the **Audit Logs** workspace page.                                    |
| **Filtering**        | Filter by search text, action, outcome, severity, event name, and date range.                 |
| **Change diffs**     | Each management change records a named event and a before/after diff, with secrets redacted.  |
| **Hash chain**       | Hourly signed digests chain the rows together, so deleted or edited rows show up in an integrity check. |
| **Export**           | Export matching entries as JSON, JSON Lines, or Syslog when the user has download permission. |
| **Retention**        | Configure how long audit log entries are kept.                                                |
| **IP omission**      | Keep the audit trail without recording client IP addresses.                                   |
| **Object storage archival** | Periodically archive audit events to S3/GCS in time-windowed, size-bounded JSONL objects for long-term, off-box, compliance-grade retention. |

## Configuration

```json
{
  "audit_logs": {
    "disabled": false,
    "hmac_key": "env.AUDIT_HMAC_KEY",
    "retention_days": 365
  }
}
```

### Configuration Fields

| Field            | Type    | Description                                                                                                                                |
| ---------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `disabled`       | boolean | When `true`, audit logging is turned off. Default: `false`.                                                                                |
| `hmac_key`       | string  | HMAC secret key used to sign audit events. Minimum 32 bytes. Supports `env.` prefix for environment variables (e.g. `env.AUDIT_HMAC_KEY`). Acts as the key with ID `default`. See [Signing keys](#signing-keys). |
| `hmac_keys`      | array   | Named signing keys, each `{ "id": "...", "key": "..." }`. `id` is 1 to 32 letters, digits, `-` or `_`. `key` is at least 32 bytes and supports `env.`. Keep retired keys here so their rows still verify. |
| `active_key_id`  | string  | ID of the key that signs new rows. Required when more than one key is configured. |
| `retention_days` | integer | Days to retain audit log entries **in the database**. `0` disables retention-based cleanup. Does not affect archived objects (see [Archiving to Object Storage](#archiving-to-object-storage)). |
| `omit_ip_addresses` | boolean | When `true`, audit logs stop recording client IP addresses and never return them. Every other field is kept. Default: `false`. See [Omitting IP Addresses](#omitting-ip-addresses). |
| `include_reads` | boolean | When `true`, every GET request is audited. When `false`, reads are audited only when they disclose a secret or export data. Default: `false`. See [What gets recorded](#what-gets-recorded). |
| `object_storage` | object  | Optional. When set, archives audit events to S3/GCS in addition to the database. Setting it is what enables archival — there is no separate on/off flag. See [Archiving to Object Storage](#archiving-to-object-storage). |
| `archive_interval` | string | Archival window size, as a Go duration string (e.g. `"6h"`). Also the nominal period of the archival job. Default: `"24h"`. Minimum: `"5m"` (lower values are clamped up). |
| `archive_grace_period` | string | How long a window is held open past its end before it may be archived, absorbing clock skew and late inserts. Must be **strictly less than** `archive_interval`. Default: `"15m"`. |
| `archive_max_object_bytes` | integer | Uncompressed JSONL size at which a new part object is started. Default: `134217728` (128 MiB). Minimum 1 MiB, maximum 4 GiB. |
| `archive_object_lock` | object | Optional. Takes `mode`, either `compliance` or `governance`, and `retention_days`, at least 1. Writes every archive object with S3 Object Lock or GCS object retention. Requires `object_storage`. See [Locking archive objects](#locking-archive-objects). |

<Note>
The `archive_*` fields only take effect when `object_storage` is configured.

`config.schema.json` constrains these fields, so an editor wired to it (via `$schema`) will flag a malformed duration like `"6 hours"` or an out-of-range `archive_max_object_bytes` as you type. The gateway itself does **not** reject such values at startup: each field is normalized independently at runtime, so a value that gets past the schema **falls back to its default or is clamped into range rather than failing startup**. A typo like `"6 hours"` silently yields the 24h default, and `archive_interval: "10s"` is quietly raised to the 5m floor.

Because a bad value fails quietly rather than loudly, confirm what actually took effect from the startup log line, which reports all three:

```
audit log archive routine started (interval: 24h0m0s, grace: 15m0s, max part size: 134217728 bytes)
```
</Note>

## What gets recorded

Every create, update and delete on the management API writes an audit event, including changes to `/api/config`.

Reads are not recorded by default, since dashboard polling would bury the changes. These reads are still recorded:

- Revealing or copying a virtual key (`/reveal`, `/copy`).
- Exporting audit logs and downloading skill bundles.
- SSO login callbacks, and any request a handler tags with an explicit action or a high severity.

Set `include_reads` to `true` to record every GET as before.

Each event also carries what changed, who acted and how:

| Field          | Description                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------ |
| `eventName`    | Named event in the form `<resource>.<verb>`, such as `virtual_key.updated`. Filterable.                       |
| `changes`      | Before/after diff of the changed fields. Returned by get-by-id and exports, left out of list responses.      |
| `severity`     | `info` for routine changes, `high` for admin actions with a large blast radius. Filterable.                  |
| `requestID`    | The request's `X-Request-ID`. Bifrost generates one when the caller sends none and returns it on the response. |
| `authMethod`   | `sso_login`, `sso_session`, `idp_token`, `auth_proxy`, `agent_token` or `api_key`.                           |
| `sessionID`    | A one-way hash of the dashboard session. It links events from one session without exposing the session itself. |
| `onBehalfOfId` | For API keys, the user who created the key. For system jobs, the user who queued the job.                    |

### Event names and diffs

Bifrost records each management change as a named event and stores a diff of the fields that changed:

```json
{
  "eventName": "virtual_key.updated",
  "severity": "info",
  "changes": {
    "fields": [
      { "path": "budget.max_limit", "old": 100, "new": 250 },
      { "path": "keys[0].value", "redacted": true }
    ]
  }
}
```

Common names include `virtual_key.created`, `virtual_key.updated`, `virtual_key.deleted`, `provider.updated`, `provider_key.updated`, `mcp_client.updated`, `plugin.updated`, `config.updated`, `proxy_config.updated`, `user.created`, `user.deleted`, `user.role_assigned`, `user.teams_updated`, `role.permissions_updated`, `api_key.created`, `edge_config.updated`, `edge_ca.rotated`, `device.deleted`, `network_trust.added` and `network_trust.removed`. Teams, customers, roles, API keys, business units, projects, guardrail rules and configs, identity providers, MCP tool groups, access profiles, alert channels and rules, circuit breaker policies, prompts, prompt folders, versions, sessions and deployments, skills, agents, webhooks and user-agent mappings get `.created`, `.updated` and `.deleted` events. Actions get their own verb, for example `virtual_key.rotated`, `webhook.secret_rotated`, `mcp_client.reconnected`, `prompt_session.committed`, `budget_request.approved`, `virtual_key.user_attached`, `business_unit.user_removed`, `logs.deleted` and `license.uploaded`.

Sign-in routes are named whether they succeed or fail: `auth.login` (password and SSO), `auth.logout`, `auth.session_refreshed`, `auth.setup_session_started`, and `auth.agent_token_issued`, `auth.agent_token_refreshed` and `auth.agent_logout` for the edge agent. A sign-in that also provisions a new user writes both rows.

Changes your identity provider pushes over SCIM are recorded as system events (`scim.user_created`, `scim.user_updated`, `scim.user_deactivated`, `scim.user_deleted` and the matching `scim.group_*` events) with initiator `system:scim`.

A request that has no named event still gets a name derived from the route, such as `virtual_key.deleted`. A write below an entity is named after the sub-route with action `update`, so `DELETE /api/governance/users/{id}/access-profiles/{profile_id}` reads `user.access_profiles_removed`, never `user.deleted`.

POST routes that only test or preview something are recorded with action `read`, so a dry run never reads as a change. `POST /api/cluster/diagnostic` reads `cluster.diagnostic_run`, and webhook tests, previews, verify and discovery calls read `.tested`, `.previewed`, `.verified` and `.config_discovered` (or `.endpoints_discovered`, `.claims_discovered`).

Role assignment, role permission changes, API key creation and updates, identity provider changes, license uploads, edge CA generation, import and rotation, and SCIM provisioning token rotation are recorded at severity `high`.

Diffs never contain secrets. A field whose name looks like a secret shows up with `redacted: true` and no values. That covers `value`, `key`, `secret`, `token`, `password`, `api_key`, `client_secret`, `private_key`, `authorization`, `cookie`, `credential`, `credentials`, and any name ending in `_key`, `_secret`, `_token` or `_password`. Provider configs, provider keys, MCP clients, identity providers and guardrail configs are diffed from their redacted forms. Fields that change on every write without anyone choosing to change them are left out: `created_at`, `updated_at`, usage counters, reset times, config hashes, and the row IDs and owner keys of nested records. Adding a budget to a virtual key reports its limit and reset window, not a dozen bookkeeping fields. A diff stops at 200 fields or 16 KB and sets `truncated: true`.

### System events

Background jobs write events too. Their initiator has type `system` and ID `system:<job>`. When a user queued the job, `onBehalfOfId` names that user.

| Event                                | When                                                                                          |
| ------------------------------------ | --------------------------------------------------------------------------------------------- |
| `directory.synced`                   | A directory or SCIM sync job finishes.                                                        |
| `identity.reconciled`                | An identity reconcile job runs.                                                               |
| `access_profile.*`                   | Access profile propagation and role apply or revoke jobs run.                                 |
| `access_profile.vk_rotated`          | Scheduled virtual key rotation runs. The outcome is `failure` if any key failed to rotate.     |
| `user.role_synced`                   | A role is synced from the identity provider. Severity `high`.                                 |
| `user.status_reconciled`             | Status reconcile deprovisions a user. Severity `high`.                                        |
| `audit.retention_purged`             | Retention deletes old audit rows.                                                             |
| `audit.window_archived`              | An archive window is written to object storage.                                               |
| `config.file_applied`                | At startup, `config.json` sections for client config, providers or MCP clients overwrite the stored config. |
| `audit.settings_changed`             | The `audit_logs` settings differ from the previous boot. Severity `high`.                     |
| `audit.logging_disabled`             | Audit logging is turned off. Written once, before logging stops.                              |

At every boot Bifrost compares the `audit_logs` settings with those of the previous boot. If they differ, it records `audit.settings_changed` with the diff. Signing keys appear only as key IDs and a short fingerprint of `hmac_key`, never the key itself. Someone who turns audit logging off to hide their tracks still leaves `audit.logging_disabled` as the last row.

## Signing keys

Bifrost signs every audit row with HMAC-SHA256. New rows use the v2 format, `v2:<key id>:<hex>`, and the signature covers every field except `tags`, `attachments` and `reason` (handlers may set these after insert), the request IP and initiator host (`omit_ip_addresses` blanks these), and `created_at`. Rows written before v2 keep their v1 signatures and still verify.

`GET /api/governance/audit-logs/{id}/verify` returns `valid`, the `algorithm` (`hmac-sha256-v1` or `hmac-sha256-v2`), the `key_id`, and a `reason` when the check fails. It no longer returns the computed and stored signatures, since a reader holding the expected HMAC could forge a matching row.

If you configure no key, Bifrost generates one, encrypts it, and stores it in the config store under the ID `generated`. Every node uses that key and it survives restarts. Earlier versions generated a random key per node on every boot, so signatures from before a restart never verified.

### Rotating the signing key

Add the new key to `hmac_keys`, point `active_key_id` at it, and keep the old key in the list:

```json
{
  "audit_logs": {
    "hmac_keys": [
      { "id": "2025-q4", "key": "env.AUDIT_HMAC_KEY_2025_Q4" },
      { "id": "2026-q1", "key": "env.AUDIT_HMAC_KEY_2026_Q1" }
    ],
    "active_key_id": "2026-q1"
  }
}
```

New rows are signed with `2026-q1`. Rows signed with `2025-q4` keep verifying as long as that key stays in the list. Remove a key and its rows can no longer be verified. The verify endpoint then returns `valid: false` with a `reason` naming the missing key.

An existing `hmac_key` keeps working as the key with ID `default`. To rotate away from it, leave `hmac_key` set, add the new key to `hmac_keys`, and set `active_key_id` to the new key's ID. Don't reuse the ID `default` in `hmac_keys`.

Bifrost refuses to start if a key is shorter than 32 bytes, a key ID is invalid, `active_key_id` names no configured key, or several keys are configured without `active_key_id`.

Rows signed with the generated key keep verifying after you configure `hmac_key` or `hmac_keys`: Bifrost still loads the generated key, under the ID `generated`, but only to verify. New rows are signed with your configured key.

## Hash chain and integrity checks

A signature proves a row wasn't edited. It can't show that a row was deleted. For that, Bifrost seals the audit log into hourly windows. Fifteen minutes after a window closes, Bifrost hashes its rows and appends a signed link that includes the hash of the previous link. The links live in the `enterprise_audit_digests` table.

The chain starts at the first boot on a version that has it. Rows written before that are not covered. When retention deletes rows it deletes whole windows and marks their links as pruned, so the chain stays checkable.

`GET /api/governance/audit-logs/integrity` rechecks the chain against the rows in the database. It takes `start_date` and `end_date` in RFC 3339, defaults to the last 24 hours, and rejects ranges over 31 days with a 400. The caller needs `AuditLogs:View` and all-data access to audit logs. A role whose audit log access is scoped gets a 403, because the report counts rows across every user.

```json
{
  "start": "2026-10-13T00:00:00Z",
  "end": "2026-10-14T00:00:00Z",
  "intact": false,
  "windows": [
    {
      "window_start": "2026-10-13T09:00:00Z",
      "window_end": "2026-10-13T10:00:00Z",
      "status": "rows_mismatch",
      "expected_rows": 412,
      "actual_rows": 409
    }
  ]
}
```

| Status              | Meaning                                                                    |
| ------------------- | -------------------------------------------------------------------------- |
| `ok`                | The rows match the sealed link.                                            |
| `rows_mismatch`     | Rows were added, removed or edited after the window was sealed.            |
| `chain_broken`      | The previous link is missing or was altered.                               |
| `signature_invalid` | The link doesn't match its signature, or its signing key isn't configured. |
| `missing`           | No link covers this span.                                                  |
| `pruned`            | Retention deleted the rows. This is expected.                              |
| `pruned_early`      | Rows were removed before the retention period ended.                       |

`intact` is `false` when any window has a status other than `ok` or `pruned`. The report lists sealed windows and windows with a problem. The first link in the chain is listed only when it fails.

## Omitting IP Addresses

Some deployments can't record where employees connect from. Employee privacy law and works council agreements, common in Germany, often rule it out. Set `omit_ip_addresses` to keep the audit trail without IPs:

```json
{
  "audit_logs": {
    "hmac_key": "env.AUDIT_HMAC_KEY",
    "retention_days": 365,
    "omit_ip_addresses": true
  }
}
```

With the setting on:

- The gateway never reads the client IP (`X-Forwarded-For`, `X-Real-IP` or the socket address) for audit events. New rows have an empty `request_ip` and initiator host.
- The initiator, action, target, path, method, user agent, outcome and duration are still recorded. HMAC signatures don't cover the IP fields, so signature verification keeps working.
- IPs in rows written before you turned the setting on are hidden from the list and detail APIs, the dashboard and every export format.
- Search no longer matches on IP, IP filters are ignored, and the filter data endpoint returns no request IPs. Otherwise a caller could filter older rows by an address to learn who used it.
- Events that object storage archival copies after the change carry no IP, including events from older rows.

<Warning>
Turning the setting on doesn't delete IPs that are already stored. Older database rows keep them until `retention_days` removes those rows. Archive objects already written to object storage also keep them. If your agreement requires those IPs to be erased, clear the `request_ip` and `initiator_host` columns of `enterprise_audit_logs` yourself, and apply your bucket's lifecycle or deletion rules to existing archives.
</Warning>

Turning the setting off again resumes IP recording for new events. Rows written while it was on stay without IPs.

## Viewing Audit Logs

Open **Governance > Audit Logs** in the Bifrost dashboard.

The table shows:

| Column        | Description                                                                                          |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| **Time**      | When the event occurred.                                                                             |
| **Action**    | The operation performed, such as create, update, delete, authenticate, authorize, export, or import. |
| **Outcome**   | The result of the operation: success, failure, or pending.                                           |
| **Initiator** | The user, API key, or system actor that initiated the action.                                        |
| **Target**    | The resource affected by the action.                                                                 |
| **Path**      | The request method and path, when available.                                                         |
| **IP**        | The request IP address, when available. Always empty when `omit_ip_addresses` is on.                 |
| **Duration**  | Request duration in milliseconds, when available.                                                    |

You can search by initiator, target, IP, or path, and filter by action, outcome, severity, start date, and end date. With `omit_ip_addresses` on, search skips IPs and the IP filter disappears. The API also filters by event name with `event_name` or `event_names`.

## Exporting Audit Logs

Users with `AuditLogs:Download` permission can export the currently filtered audit log results from the dashboard. The export endpoint enforces the same permission, so a role with only `AuditLogs:View` gets a 403 from the API as well.

Supported export formats:

| Format            | Use Case                                                     |
| ----------------- | ------------------------------------------------------------ |
| JSON              | Structured review or ad hoc processing.                      |
| JSON Lines        | Line-delimited ingestion pipelines.                          |
| Syslog (RFC 5424) | SIEM or log-forwarding pipelines that accept syslog records. |

Exported events include the `changes` diff. With `omit_ip_addresses` on, exports contain no IP addresses in any format. The syslog `clientIP` parameter is left out.

## Event type URI

Every audit event has a `typeURI` field. New events use `https://getbifrost.ai/schemas/auditlog.json`. Older events keep `http://schemas.bifrost.io/audit/api/v1`.

Stored events are not rewritten, so exports and searches that cover both periods return both values. If a SIEM rule matches on `typeURI`, make it accept both.

## Archiving to Object Storage

By default, audit events live only in the database, which is the source of truth for everything you see in the dashboard (viewing, filtering, HMAC verification, and export). Databases, however, are not ideal for multi-year compliance retention or off-box durability.

When you configure `object_storage`, a background job **additionally** copies every audit event to an S3-compatible bucket (S3, GCS, MinIO, R2), one time window at a time. This is a copy, not an offload: the full event ends up in **both** the database and object storage, so each store holds a complete, independent copy.

<Note>
This differs from [Log Exports](/enterprise/log-exports), where object storage *offloads* the heavy request/response payload out of the database. For audit logs, object storage is a complete **mirror** — the database is never trimmed of data by enabling it.
</Note>

### Database vs. Object Storage

| Concern | Database | Object Storage |
| ------- | -------- | -------------- |
| Role | Source of truth | Durable archive |
| Used by dashboard / API / export / HMAC verify | Yes | No |
| Contents | Full event | Full event (identical copy) |
| Retention | Governed by `retention_days` | Governed by your bucket's lifecycle rules |
| When populated | Immediately (buffered, sub-second) | Only when `object_storage` is configured, **going forward** (no backfill), and only once a window closes — so the archive trails the database by at least `archive_interval + archive_grace_period` |

Because the two are decoupled, the archive can outlive the database: once `retention_days` deletes an old row, its object in the bucket is left untouched. Use [`archive_object_lock`](#locking-archive-objects) and bucket lifecycle rules to govern how long the archive is kept.

<Warning>
Retention and archival are **independent** loops — the cleaner deletes by age and does not wait for a window to be archived. Keep `retention_days` comfortably larger than `archive_interval + archive_grace_period`, or rows may be deleted from the database before they are ever copied to the bucket. With the defaults (24h window, 15m grace) the shortest safe setting is `retention_days: 2`; `retention_days: 1` races the archiver.
</Warning>

### How Archival Works

Archival runs as a **periodic background job**, not as part of the request path. Time is divided into fixed windows of `archive_interval`, and each closed window is archived as a unit, in order:

1. **A window closes.** The window `[start, end)` becomes eligible only once `end` is further in the past than `archive_grace_period`. The grace period absorbs clock skew and rows that land slightly late, so a window is not archived while events may still be arriving for it.
2. **A job is enqueued.** One job archives one window. Job IDs derive from the window bounds, so in a multi-node cluster every node can tick while exactly one job row is created and exactly one node runs it — no leader election or lock is involved.
3. **Rows are streamed into part objects.** Committed rows in the window are streamed from the database and encoded as JSON Lines. A new part is rolled each time the accumulated uncompressed JSONL crosses `archive_max_object_bytes`; a part boundary never splits a JSON line.
4. **A manifest commits the window.** After every part has been durably stored, a `manifest.json` listing exactly those parts is written. The manifest is the **commit point** — only once it lands does the archival watermark advance to `end`, making the next window eligible.

Objects for a window live under a single window prefix:

```
{prefix}/audit-logs/{YYYY}/{MM}/{DD}/{start}-{end}/part-00000.jsonl[.gz]
{prefix}/audit-logs/{YYYY}/{MM}/{DD}/{start}-{end}/manifest.json[.gz]
```

For example, with `"prefix": "acme-prod"`, `"compress": true`, and a 24h interval:

```
acme-prod/audit-logs/2026/07/14/20260714T000000Z-20260715T000000Z/part-00000.jsonl.gz
acme-prod/audit-logs/2026/07/14/20260714T000000Z-20260715T000000Z/part-00001.jsonl.gz
acme-prod/audit-logs/2026/07/14/20260714T000000Z-20260715T000000Z/manifest.json.gz
```

| Key segment | Meaning |
| ----------- | ------- |
| `{prefix}` | The configurable base path from `object_storage.prefix` (default `bifrost`). |
| `audit-logs` | Fixed segment so audit objects never collide with request logs (`logs/`, `mcp-logs/`). |
| `{YYYY}/{MM}/{DD}` | UTC date of the window's **start** — enables lifecycle rules and prefix-scoped queries (Athena, SIEM ingestion). |
| `{start}-{end}` | The window's UTC bounds in compact ISO-8601 (`20060102T150405Z`), so windows sort chronologically in a bucket listing. |
| `part-00000` | Zero-padded part index, ordered. A window has as many parts as `archive_max_object_bytes` requires. |
| `manifest.json` | The window's commit record. Written last; see below. |
| `.gz` | Present only when `compress` is enabled. |

Every object also carries tags (`type`, `window_start`, `window_end`, `count`, and `part`/`parts`) so lifecycle rules and consumers can select objects without listing and pattern-matching keys. Manifests are tagged `type=audit-logs-manifest`, parts `type=audit-logs`.

#### Reading the Archive

**Always read a window through its manifest, and ignore any object the manifest does not list.** A retried window can leave behind an orphaned part from an earlier attempt; the manifest lists exactly the parts that belong to the window, which is what makes it authoritative.

```json
{
  "version": 2,
  "window_start": "2026-07-14T00:00:00Z",
  "window_end": "2026-07-15T00:00:00Z",
  "event_count": 128402,
  "compressed": true,
  "completed_at": "2026-07-15T00:15:04Z",
  "parts": [
    { "key": "acme-prod/audit-logs/2026/07/14/.../part-00000.jsonl.gz", "event_count": 96311, "bytes": 134217508, "sha256": "9f2c..." },
    { "key": "acme-prod/audit-logs/2026/07/14/.../part-00001.jsonl.gz", "event_count": 32091, "bytes": 44821904, "sha256": "41ad..." }
  ],
  "rows_hash": "c3e1...",
  "retain_until": "2033-07-15T00:15:04Z",
  "key_id": "2026-q1",
  "signature": "7b90..."
}
```

Version 2 manifests let you check an archive without the database. Each part's `sha256` is the hash of its uncompressed JSONL. `rows_hash` hashes the window's rows the same way the [hash chain](#hash-chain-and-integrity-checks) does, and `signature` is an HMAC over the manifest made with the key named by `key_id`. `retain_until` is set only when [object lock](#locking-archive-objects) is on.

A window that contained no events still gets a manifest, with an empty `parts` array — a positive record that the window was examined and held nothing. The absence of a manifest means the window is **not** yet committed, not that it was empty.

#### Delivery Guarantees

| Property | Behavior |
| -------- | -------- |
| **Archive-only** | The job never deletes database rows. Retention stays governed by `retention_days`. |
| **At-least-once** | A window commits only after its manifest is durably written, so a crash re-runs the window. Object uploads are retried (3 attempts, exponential backoff), and a window that fails outright is retried on the next pass with the watermark left untouched — archival does not skip ahead past a failure. |
| **Contiguous** | Exactly one window is in flight at a time, so committed windows never skip a gap. |
| **First complete write wins** | Once a window has a manifest, a retry keeps the committed archive as-is. Fields enriched *after* a window was committed are deliberately not re-archived. |
| **No backfill** | On first run a marker records the starting watermark. Audit events written **before** you enabled `object_storage` are never copied to the bucket. |

<Info>
Unlike the earlier per-flush implementation, archival is **no longer best-effort** — a failed upload is retried rather than logged and dropped, and the watermark will not advance past a window that did not commit. The database nevertheless remains the source of truth: it is what the dashboard, API, export, and HMAC verification read, and it is written independently of whether the bucket is reachable. Object-storage problems delay the archive; they never block audit logging or request handling.
</Info>

#### Tuning

- **`archive_interval`** trades archive freshness against object count. Longer windows mean fewer, larger objects and a longer lag before events reach the bucket; shorter windows mean fresher data and more objects. The job wakes at least hourly regardless, so a window that closes shortly after a tick is not left waiting a full 24h.
- **`archive_max_object_bytes`** bounds peak memory: a part is buffered in memory before upload, so expect roughly **2× this value** per archiving node when `compress` is enabled (compression allocates a second buffer). The 128 MiB default implies a ~256 MiB peak. Raise it for fewer, larger objects on nodes with headroom; lower it on memory-constrained nodes.
- **`archive_grace_period`** rarely needs changing. Raise it if you run with meaningful clock skew across nodes.

### Locking archive objects

Set `archive_object_lock` to make the archive write-once. Bifrost writes every part and manifest with S3 Object Lock or GCS object retention, retained for `retention_days` from the time it is written:

```json
{
  "audit_logs": {
    "hmac_key": "env.AUDIT_HMAC_KEY",
    "retention_days": 365,
    "object_storage": {
      "type": "s3",
      "bucket": "acme-audit-archive-locked",
      "prefix": "acme-prod",
      "region": "us-east-1"
    },
    "archive_object_lock": {
      "mode": "compliance",
      "retention_days": 2555
    }
  }
}
```

`mode` is `compliance` or `governance`, as defined by your storage provider. `retention_days` must be at least 1.

Create the bucket with Object Lock enabled (S3) or object retention enabled (GCS). Bifrost checks this at startup. If the bucket doesn't support it, Bifrost logs an error and runs without archival.

A locked part can't be overwritten, so a retried window writes its parts under new keys, `part-00000-<attempt>.jsonl`. The failed attempt's parts stay in the bucket as orphans until their lock expires. The manifest lists only the committed parts. Lifecycle rules can't delete a locked object before its `retain_until`.

<Warning>
In `compliance` mode nobody can delete a locked object before it expires, including the bucket owner and the root account. Set `retention_days` to what your compliance requirement asks for and no more, since storage for those objects can't be reclaimed early.
</Warning>

#### Object Storage Fields

| Field | Type | Required | Description |
| ----- | ---- | -------- | ----------- |
| `type` | string | Yes | Backend type: `s3` or `gcs`. |
| `bucket` | string | Yes | Bucket name. Supports `env.` references. |
| `prefix` | string | No | Configurable base key path; `audit-logs/` is appended under it. Default: `bifrost`. |
| `compress` | boolean | No | Gzip stored objects (objects use a `.jsonl.gz` extension). Default: `false`. |
| `region` | string | No | AWS region (S3). Supports `env.` references. |
| `endpoint` | string | No | Custom S3-compatible endpoint for MinIO/R2. Supports `env.` references. |
| `access_key_id` | string | No | AWS access key ID. Omit to use the default credential chain (instance role, env vars). Requires `secret_access_key`. |
| `secret_access_key` | string | No | AWS secret access key. Supports `env.` references. |
| `session_token` | string | No | STS temporary session token. |
| `role_arn` | string | No | IAM role ARN for STS AssumeRole. |
| `force_path_style` | boolean | No | Path-style URLs (required for MinIO). Default: `false`. |
| `credentials_json` | string | No | GCS service account JSON or file path. Omit to use Application Default Credentials. |
| `project_id` | string | No | GCP project ID override (GCS). |

<Note>
You can point audit archival at its own dedicated (ideally write-once/locked) bucket, or reuse the same bucket as request `logs_store` with a distinct `prefix`. The `audit-logs/` path segment keeps the two from overlapping.
</Note>

If the object store cannot be reached at startup, Bifrost logs the error and continues **without** archival — audit logging to the database is never blocked by object-storage problems.

The watermark is persisted, not held in memory, so archival **resumes where it left off** after a restart or an outage: windows that closed while the archiver was down are archived on subsequent passes until it catches up. Nothing is skipped — provided the rows are still in the database, which is what the `retention_days` guidance above protects.

Catch-up is paced, though: each pass enqueues **one** window, and passes run every `archive_interval` (capped at hourly). After a long outage, expect a backlog of *N* windows to take roughly *N* passes to drain — so a multi-day outage with a 24h interval clears at about one window per hour, not all at once.

On shutdown the archiver stops before the object store is released, and an in-flight window is allowed to finish rather than being cancelled, so parts are never left behind without a manifest.
